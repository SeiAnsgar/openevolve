## Experiment Results Data Structure Documentation

### Overview
The primary purpose of each test run is to map a deep learning model (**workload**) onto a Compute-in-Memory (**CIM**) hardware architecture according to a specified optimization target.

#### Data Structure Schema

The data structure uses a YAML format structured around distinct test identifiers (`test_<testname>`). Below is the standard template:

```yaml
test_<testname>:
    workload: <string>
    hardware: <string>
    opt_goal: <string>

    OpenEvolve:
        configuration:
            number_of_iterations: <integer>
            LLM_backend: <string>
        metrics:
            energy: <float>
            latency: <float>
        time: <string>

    ZigZag:
        configuration:
            nb_spatial_mappings: <integer>
        metrics:
            energy: <float>
            latency: <float>
        time: <string>
```

#### Field Definitions
* **`workload`**
  * The target neural network or model to be mapped (typically a `.onnx` file name or descriptor).

* **`hardware`**
  * The target hardware specification, defined via a CIM (Compute-in-Memory) hardware description file or identifier.

* **`opt_goal`**
  * The primary metric targeted during optimization (`"latency"` or `"energy"`).
  * *Note / Open Point:* Clarify whether "energy" refers to total energy consumed or energy transferred during computation.

#### OpenEvolve Configuration

* **`number_of_iterations`**
  * The total number of evolution/optimization iterations requested for the run.

* **`LLM_backend`**
  * The Large Language Model instance used to propose candidate solutions.
  * Models hosted via ScaDS.AI (e.g., `Qwen/Qwen3-Coder-30B-A3B-Instruct`) are selected based on availability, access permissions, and task capabilities.

### Metrics and Outputs

* **`latency`**
  * Execution delay resulting from the mapping solution generated by the tool, measured in clock cycles.

* **`energy`**
  * Energy consumption calculated for the mapping solution, measured in `pAmp` (or picojoules depending on physical unit conversion; verify exact scale).

* **`time`**
  * Total wall-clock time taken by the optimization tool to complete the search process (e.g., `"23m34s"`, `"1h18m43s"`).
  * Runtime comparison between OpenEvolve and ZigZag should be interpreted with caution. OpenEvolve runs with high iteration counts may finish unexpectedly quickly if a significant portion of iterations fail early due to syntax or validation errors during program candidate evaluation.
